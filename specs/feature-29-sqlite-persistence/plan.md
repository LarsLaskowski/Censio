# Plan: SQLite persistence for the server

Source: Issue #29 | [spec.md](spec.md)
Tier: security — the change creates a permission control (owner-only modes of the database file, its side files and a folder it creates, which hold private names) beside a new dependency with native code.
Security areas touched: a new area "Server database" (file, folder, modes, the setting `Censio:Database:File`); Logging and showing external data (the server's database log lines and EF Core's log categories); Network exposure (`src/Censio.Server/Dockerfile`, publish changed); Docker/CI (`src/Censio.Server/Dockerfile`, `.github/scripts/image-check.sh`); build configuration (`Directory.Packages.props`, `src/Censio.Server.Data/Censio.Server.Data.csproj`, `.config/dotnet-tools.json`, a project section of `.editorconfig`); dependencies (`Microsoft.EntityFrameworkCore.Sqlite` 11.0.0 with `SQLitePCLRaw.bundle_e_sqlite3` 3.0.5 and the native SQLite 3.53.4, `Microsoft.EntityFrameworkCore.Design` 11.0.0, the tool `dotnet-ef` 11.0.0).

## Approach

**Packages and build.** `Directory.Packages.props` gets `Microsoft.EntityFrameworkCore.Sqlite` and
`Microsoft.EntityFrameworkCore.Design` 11.0.0; `Censio.Server.Data.csproj` references both (the design package
`PrivateAssets="all"`) and `Censio.Contracts`. `.config/dotnet-tools.json` pins `dotnet-ef` 11.0.0. The initial
migration is generated into `src/Censio.Server.Data/Migrations/` with `dotnet tool run dotnet-ef migrations add
InitialSchema --project src/Censio.Server.Data`, through an internal `IDesignTimeDbContextFactory`; a section
`[src/Censio.Server.Data/Migrations/**.cs]` with `generated_code = true` follows the paths block of `.editorconfig`.
`appsettings.json` sets `Microsoft.EntityFrameworkCore` to `Warning`. The Dockerfile restores and publishes with
`-r linux-musl-x64 --self-contained false`, the publish also with `-p:UseAppHost=false` (the entry point is `dotnet
Censio.Server.dll`), so the image carries one native SQLite instead of 31 (fact 7).

**Schema** (internal `CensioDbContext`, entities configured in `OnModelCreating`, no public `DbSet`): `Profiles` (id,
name nullable); `Ticks` (number = rowid, id unique, profile, receive time as UTC ticks INTEGER, game time); `Islands`
(profile and key unique, latest name with the receive time and tick number it came from); `TickIslands` (tick,
position, key, session ID, name); `TickEntries` (tick island, position, product GUID, eight floats, three int32);
`TickMapPairs` (entry, kind workforce or building, GUID, amount); `Catalog` (one row: identity, document); `Icons`
(reference key, PNG). A float is its `BitConverter.SingleToInt32Bits` pattern in an INTEGER column, `NULL` for no value
(record 0067). Receive times are INTEGER so that ordering happens in SQL.

**Opening** (`ServerDatabase.OpenAsync`), in this order, every step before 5 read-only on an existing file:
1. No file: an in-memory shared-cache database of a unique name with one keeper connection for the lifetime, migrated,
   kind `InMemory`.
2. A missing folder is created (Linux `0700`), a missing file is created empty with `FileMode.CreateNew` (Linux
   `UnixCreateMode` `0600`) before SQLite opens it, so SQLite's side files take that mode (fact 12); the connection is
   opened with mode `ReadWrite`, never `ReadWriteCreate`, from a `SqliteConnectionStringBuilder` (`DataSource` the full
   path, `Mode` `ReadWrite`), never by text concatenation. `IOException`/`UnauthorizedAccessException`: `NotWritable`.
3. Classification over a raw connection: user tables of `sqlite_master` (every entry whose name does not start
   with `sqlite_`, of any type: table, index, view, trigger; "only the two EF tables" then means exactly those two and
   EF's indexes on them; the bookkeeping-only test adds a case with an extra view, refused as E3). `SqliteException` 26 or 11: `NotADatabase`;
   any other `SqliteException`: `NotWritable`. No user table, or only `__EFMigrationsLock` and an empty
   `__EFMigrationsHistory` (a first update that failed or stopped): fresh. Tables without `__EFMigrationsHistory`, or a first
   applied migration other than the initial one: `NotADatabase`. An applied id the migrations assembly does not list:
   `NewerSchema`.
4. Write probe: `BEGIN IMMEDIATE`, `CREATE TABLE` of a probe table, `ROLLBACK` (fact 11): failure `NotWritable`.
5. Pending migrations: the commands of each are generated first (`IMigrationsSqlGenerator`); one with
   `TransactionSuppressed` gives `UpdateFailed` without running anything (record 0065), then `Database.MigrateAsync`;
   any exception `UpdateFailed`. Before `MigrateAsync` the opener deletes every row of `__EFMigrationsLock` when the
   table exists, unconditionally (fact 10; one process per file, N6). If fact 9 is refuted, the Dev runs the generated
   script (`MigrationsSqlGenerationOptions.NoTransactions`) in one own `SqliteTransaction` instead and reports the
   deviation. After a failed first update of a new or empty file the two bookkeeping tables remain (spec E5).
6. `PRAGMA journal_mode=WAL` (file only); synchronous stays `FULL`, so a tick reported stored survives a power loss.
7. Kind: file created in step 2 `Created`; migrations applied to an existing file `Updated`; otherwise `Opened`.
   A failed open disposes what it opened and clears the connection pool.

Context options: `UseSqlite`, `UseLoggerFactory(loggerFactory)`, never sensitive data logging, then the optional
`configureContext` (the tests' seam for `ExtendedMigrationsAssembly`). Disposal clears the pool so the file and its
side files are closed.

**Store** (`ServerStore`). A write gate (`SemaphoreSlim`, one per `ServerDatabase`) serializes writes; in memory every
read takes it too (record 0066). A write runs in one `BEGIN IMMEDIATE` transaction over the context's connection with
prepared commands reused per row kind (record 0067): tick id present: `AlreadyStored`, nothing written; `INSERT OR
IGNORE` the profile without a name; insert the tick, its islands, entries and pairs; upsert each `Islands` row when
(receive time, tick number) is not older than the stored one. `SqliteException` or `DbUpdateException`: rollback,
`Failed` with the exception (E8); cancellation propagates. `StoreProfileAsync` upserts the name. Reads use a new
context with `AsNoTracking` or a data reader; a tick reads back in stored positions, maps rebuilt ascending. Latest
tick: `ORDER BY` receive time, then tick number, descending. `FindMissingIconsAsync` returns the missing references
distinct and ordinally sorted; it passes the references either as parameters, one per reference, chunked below SQLite's
32,766 (a catalog upload names at most 16,384, `contract.md`, *Bounds*), or as one JSON parameter through `json_each` on a
raw command, never as SQL text; the area document states which. A read failure surfaces as the provider's exception (no criterion asks otherwise; the
area document says so).

**Server** (`DatabaseSetup`). File: `Censio:Database:File` when set (not fully qualified, the empty string included:
E1 line, `null`), else `<full data directory>/censio.db`, else `null` (in memory). `ReportOpenResult` writes one line
per kind, with the texts of S1 to S5 and E2 to E5 (spec), `{DatabaseFile}` as the placeholder, the exception attached
for `NotWritable`, `NotADatabase`, `UpdateFailed`; `Created`/`Opened`/`Updated` at `Information`, `InMemory` at
`Warning`, failures `Critical`. `Program.cs` calls `TryOpenAsync` after the ingest token and holds the database with
`using` until the host stops; `null` returns 1.

Log line layout: one line each, exactly the spec's texts; no other new user-visible output.

**Image.** The project files and the Dockerfile change, so the Dev runs the *Image build check* (restore-order
reproduction with `-r linux-musl-x64`) and states the publish size before and after (fact 7). `image-check.sh` gets
the cases `I29-AC1` (after the first start `/config/censio.db` exists and `docker logs` holds the created line),
`I29-AC2` (the container started again on the volume logs the opened line) and `I29-AC6` (`stat -c %a` gives `600` for
`/config/censio.db`, and for `-wal` and `-shm` when present),
which only CI runs (AC1, AC2, AC6 in the image, and the native library on Alpine).

## Options considered

- Schema: created once without migrations; own SQL scripts; update a copy — lost (record 0065).
- Location: data directory only; a temporary file without a data directory — lost (record 0066).
- Tick layout: one JSON or binary blob per tick; rows through the change tracker — lost; floats as REAL or REAL without
  affinity — lost (record 0067).
- Store API on contract types versus own entities in the API: contract types won — #30 stores exactly what the reader
  accepted and the read-back equality is a direct comparison; the entity classes stay internal.
- Image: portable publish (+54.9 MB natives) versus `-r linux-musl-x64`: the second won; the image is linux/amd64 only
  (record 0026).

## Security considerations

- [x] Limits: the store takes only messages the contract reader accepted, so its bounds are the contract's (measured on
  the raw input, before decoding); the store adds none. The icon references of `FindMissingIconsAsync` go into
  parameters (one per reference, or one JSON parameter), never into SQL text.
- [x] Exceptions that reach a user-visible text: none. The exception of `NotWritable`, `NotADatabase` and
  `UpdateFailed` is attached to the `Critical` line for the operator; at start the file holds no name that a message of
  SQLite could quote. Values never enter SQL text: every write and read is parameterized.
- File modes are set at creation, never after, so no window exists in which the file is readable by others; an
  existing file or folder keeps its mode. Windows: the file takes its folder's rules, as the token file does.
- Paths come from configuration only, never from a message.
